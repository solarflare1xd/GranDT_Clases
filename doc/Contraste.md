Todo comienza con los Modelos, que son clases sencillas como Jugador, Plantilla o Usuario. Estas clases actúan como el molde o la estructura pura de mis datos y no contienen ninguna lógica ni conexión a la web(ojo hay excepciones); simplemente definen qué propiedades tiene cada elemento del juego.
A partir de ahí entra la capa de Acceso a Datos, organizada mediante los repositorios e interfaces como IJugadorRepository. Al usar una interfaz, se logra que el sistema no dependa directamente de cómo se guardan los datos, sino de qué operaciones están disponibles para consultar, agregar o borrar.
Sobre esta base se apoya la capa de Servicios, donde vive toda la lógica de negocio. Es aquí donde se aplican las reglas reales de GranDT: validar si a una plantilla le alcanza el presupuesto para comprar a un futbolista, verificar que no se agregue un jugador duplicado o controlar la cantidad de titulares. El servicio no sabe cómo se reciben las peticiones web ni cómo se consulta la base de datos; únicamente toma la información, aplica las reglas del juego e interactúa con el repositorio.
Finalmente, en la cima de la cadena alimenticia se encuentra la API o Controladores. Esta capa funciona como la puerta de entrada para los usuarios o clientes que consumen la aplicación. Su trabajo se limita a recibir la petición HTTP (como un GET o un POST), entregársela al servicio para que procese la regla correspondiente y responderle al cliente con un código adecuado, como un 200 OK si salió bien o un 400 Bad Request si falló alguna validación.
